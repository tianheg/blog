备份是长期主义的事：数据攒了十年，恢复只需要一次。这篇放两样东西——从实践里抽出来的通用原则，和我自己这套版图与取舍。它会长期迭代，每次改动记在文末。

## 原则

七条，都不绑具体工具：换一套技术栈，它们依然成立。

### 1. 先定性语义：镜像还是归档

**镜像**是目标端跟随源端——改名跟改名，删除跟删除；**归档**是只增不减。

镜像省空间、只有一个事实源、不用每次判断该留哪份，代价是源端误删会立刻反映到备份上。归档更像时间机器，代价是空间和长期堆积。

所以**选了镜像，就必须在存储侧叠加快照**，否则被删掉的那个文件会在两边同时消失。我这条链路选的是镜像加快照。

### 2. 同地同介质的两份，等于一份

3-2-1 里的「3」最容易凑出假象：同一台机器上的两块盘、同一个云账号下的两个桶，都只算一份。

要防场地级灾难（火灾、地震、盗窃、账号被封），至少一份得在异地或离线。**快照能救误删，救不了机房出事**——两者不互相替代。

### 3. 静默不等于成功

无人值守的备份，默认失败模式是**安静地停摆**：脚本不报错、日志没异常、也没有任何输出——因为上游那台机器根本没开机。

只报告「做了什么」的系统会一直安静下去。要有「多久没成功过」这类外显信号（陈旧度、心跳），而且要能区分「今天没有变化」和「今天没跑成」——这两件事在输出上长得一模一样。

### 4. 自动删除必须带刹车

自动化最危险的失败不是报错，而是**它照你的意图执行了破坏**。

两个闸门就够：单次删除量超过总量的某个比例就停下来、要求显式放行；源端文件数骤降（路径配错、目录被清空）直接拒绝执行。前者防手滑，后者防灾难。

### 5. 校验分两层：清单层与校验和层

清单层只回答「在不在」——文件名加字节数。校验和层回答「坏没坏」。

只做前者，位翻转、落盘截断这类静默损坏永远不会暴露：备份看起来完好，等到真要还原的那一刻才知道。规模不大时，全量校验和是可行的——几千个文件、几 GB，几分钟跑完。

### 6. 成功率由上游在线决定

当唯一事实源是一部手机或一台笔记本，备份什么时候完成不由你定。

两条路：让备份端密集重试，上游任何一个醒着的窗口都能赶上；或者接受断续，但必须监控停摆（见第 3 条）。**把任务定死在某个固定时刻，通常只是把失败藏起来。**

### 7. 不验证，等于没有

「命令返回成功」不等于「目标端真的有了」。

验收要读**目标端的实际状态**：重新列一遍目录、比对差异、确认归零。而不是解析命令自己打印的「已完成」。这条同样适用于自动化里的每一次自检——它打印的成功，和它实际做到的事，是两回事。

## 我的版图与取舍

四类数据，性质不同，做法也不同。这里只写结构与理由，具体参数不公开。

### 照片原图

- **事实源**：手机拍完，同步到一台笔记本上的照片目录；原图只此一份
- **备份**：1:1 镜像到 Hetzner StorageBox，存储侧开快照兜误删
- **保留**：全量（跟随源端增删）
- **为什么**：照片只增不减、增长快，镜像省空间；已按年份分目录，结构稳定
- **短板**：笔记本不开机的那天，上游就断了——靠密集重试加停摆告警兜住
- **试过与没采用的**：手机端直推存储箱、桌面端手工 rclone 同步、用支持 WebDAV 的文件管理器手动上传。放弃的共同原因是它们让「照片有几份、在哪儿」变成需要人记着的事：直推绕过了本地那份唯一事实源，手工同步依赖人记得做，两者都会让「备份」和「原件」的边界变模糊。现在的链路里，本地那份永远是事实源，备份只是它的影子

### 笔记与代码

- **事实源**：本地 git 仓库（笔记、博客、dotfiles、日记）
- **备份**：多个远端（自托管 git 服务 + 境外托管）+ 离线副本
- **为什么**：文本体积小，**版本历史本身就是时间机器**，不需要镜像语义，也不需要额外快照
- **短板**：远端地址和凭据是弱点，凭据必须能独立恢复

### 自托管服务的运行数据

- **对象**：Agent 的配置、技能库、会话库，以及各服务的数据库 dump
- **备份**：全量归档（打包）→ 对象存储；配置另走 git 单独版本化
- **保留**：滚动若干份，两地同步淘汰
- **为什么**：这类数据要能回到「某一天的整套状态」，所以用归档而不是镜像；配置单独走 git，是因为它需要逐行 diff

### 账号与凭据

- **做法**：加密数据库 + 同步到随身设备
- **为什么**：凭据丢失是所有单点故障里最致命的那个。比「备份凭据」更重要的是想清楚：**恢复凭据需要什么，以及那把钥匙不能和它放在一起**
