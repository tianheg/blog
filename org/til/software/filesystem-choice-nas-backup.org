#+TITLE: NAS 与备份场景：ext4、btrfs、ZFS 怎么选
#+DATE: <2026-11-04 23:27:51>
#+STATUS: draft
#+HEADER: Linux

结论先行：多盘 NAS 用 ZFS，单盘或小容量用 btrfs，移动硬盘和冷备用 ext4。

* 三者的本质差别

| 维度 | ext4 | btrfs | ZFS |
|------+-------+-------+-----|
| 数据校验（防静默损坏） | 无 | 有，RAID1 能修 | 有，冗余布局能修 |
| 快照 | 无（靠 LVM） | 有，轻量 | 有，零成本 |
| 增量复制 | rsync，无一致性保证 | ~btrfs send~ | ~zfs send~，最强 |
| 在线扩容 | 靠 LVM | 可以加盘 | 只能加 vdev，单盘不能扩容量 |
| 内存需求 | 低 | 中 | 高，ARC 建议 ≥8G |
| RAID5/6 | mdadm | 有 write hole，不推荐 | raidz1/2/3，成熟 |
| 出事能不能救 | 任何系统都能读 | 工具链一般 | 依赖 ZFS 工具，跨平台差 |

* 为什么 ZFS 对 NAS + 备份最优

不是因为 RAID，是因为 ~zfs send/recv~ ：

- 快照保证一致性：数据库、正在写的文件，快照那一刻就是一个完整状态
- 增量按变化块传输，不是 rsync 那种比对整个文件树
- 断点续传、可加密、可压缩后传
- 接收端可以直接挂载检查

备份最怕的是「备份下来的东西是坏的」。ZFS 的 checksum 在恢复时能逐块验证，定期 ~scrub~ 会主动扫出静默损坏；ext4 上你永远不知道某个文件是不是三个月前就悄悄坏了。

代价是内存。ARC 默认吃一半物理内存，1T 数据配 8G 是合理起点。

* 为什么 btrfs 不该被完全排除

ZFS 的硬伤是单盘用没意义（只能发现损坏，修不了），而且不能单盘扩容量。只有一块盘、或者打算「先一块以后加盘」时，btrfs 更合适：

- 单盘就有快照和校验
- ~btrfs device add~ 可以后期把单盘变成 RAID1
- 内存需求低得多

只要避开 RAID5/6，只用 single、RAID1、RAID10，btrfs 是可靠的。它的坏名声基本都来自 RAID5 的 write hole。

* 为什么 ext4 仍有位置

- 移动硬盘 / USB 冷备：掉线、拔插、跨机器读，ext4 最省心，真出问题任何 Linux 救援盘都能读
- PVE 系统盘 / 虚拟机磁盘：LVM thin + ext4 是成熟组合，虚拟化层已经提供快照
- 跨平台：Windows 读 ext4 有工具，读 ZFS/btrfs 基本没戏

* 落地建议

- 多盘 NAS：ZFS，raidz1（3 盘起）或 mirror（2 盘），配 ~sanoid~ 做自动快照 + ~zfs send~ 到异地
- 只有一块盘又想要快照：btrfs single，后期能加盘升级为 RAID1
- 移动硬盘 / 冷备盘：ext4

* 三者都不是备份方案

ZFS 的快照和 RAID 都在同一台机器上，机器烧了一起没。真正的备份是「三份、两种介质、一份异地」—— 文件系统只负责让备份拿得出一致的、可验证的副本，它本身不是备份。
